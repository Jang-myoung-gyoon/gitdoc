# GitDoc desktop updates

Install GitDoc 0.1.4 over the existing 0.1.3 install to enable update checks. On macOS, quit GitDoc and replace GitDoc.app in Applications. On Windows, run the installer from the official release for the same user and installation directory. The Inno Setup AppId remains the same. Keep the existing database path, including any custom DOCVERS_DB setting.

While the app is open and idle, GitDoc checks for information once at startup and again after 24 hours. Open **설정 → 업데이트 확인…** to view a release. On macOS, approve installation after closing other active GitDoc editing sessions. For unsigned Windows releases, use the official download link and run the installer yourself. The automatic check only fetches release information.

## macOS release gate

GitDoc embeds the pinned Sparkle 2.10.1 framework. It verifies EdDSA signatures on the feed, its release notes and downloaded archive. Sparkle installs the matching application and restarts the launcher after user approval. The distribution job continues to use the existing Developer ID and notarization credentials.

1. Store GitDoc’s private signing key as exported by Sparkle in the Actions secret `GITDOC_SPARKLE_PRIVATE_SEED`. Set the paired base64 public key as the repository variable `GITDOC_SPARKLE_PUBLIC_KEY`. The workflow also recognizes `SPARKLE_PUBLIC_KEY` and the private key names `SPARKLE_PRIVATE_KEY` and `SPARKLE_EDDSA_PRIVATE_KEY`. Keep a secure backup of the private key. The signed build must keep the same bundle identity and a valid Developer ID signature. Losing the update key can require another manual installer.
2. Run the signed build and notarization workflow with the next release tag. The signing helper checks the public/secret pair and refuses to generate a feed unless the Developer ID disk image is verified and has a stapled notarization ticket.
3. Publish the DMG and `gitdoc-macos-arm64-appcast.xml` together as assets of the latest stable GitHub release. Include the appcast on each subsequent stable release. The app reads the appcast at the stable `releases/latest/download/` address. Generate and sign the feed again whenever the DMG or included release notes change.
4. Verify two separately signed and notarized test versions with an approved test feed before shipping. Verify path replacement, restarts and document history, including interruption and an invalid signature. The local test suite exercises EdDSA signing and rejection and uses only ephemeral fixture keys.

## Windows release gate

The current workflow declares unsigned Windows distribution. This package omits publisher pins and offers version checks and an official GitHub download link. The Windows packaging job checks that the EXE is unsigned and that reinstalling at the previous location preserves GitDoc data. Enable the signed policy only when an approved signing and timestamping step is available.

When signed distribution is enabled, GitDoc reads the stable GitHub release for the x64 Windows package. After approval it downloads the exact selected asset, checks its length and SHA-256, then requires Windows Authenticode to report the file as valid and checks its signer certificate against the pin included in the installed application. The downloaded file carries its Internet zone for the Windows shell and SmartScreen. The supervisor waits for GitDoc to exit, reruns verification while holding the file read-only, and invokes the existing per-user installer at the same install path. It restores the previous application components on setup failure and restarts with the outcome. User data belongs outside the application folder.

1. Obtain or authorize an existing valid Windows Authenticode code-signing identity through the release owner. Set `GITDOC_WINDOWS_UPDATE_SIGNERS` to its lowercase SHA-256 hash over the certificate’s DER bytes. Up to two space-separated pins allow a planned rotation. The first signed Windows release must already embed the approved pin. Signed packaging fails if no pin is provided, and its installed smoke test compares the embedded pins. To move from an unsigned release to a signed one, install the first signed package manually. For a later rotation, first ship a build with both pins before replacing the old signer. Keep private keys outside GitDoc.
2. Sign and timestamp the built installer with that identity. The current pipeline builds the installer, and the signing step requires an approved Windows signing environment. Verify it with `./packaging/check-windows-update.ps1 -Setup <signed-installer> -Signers <pins>` before publishing it. Verify the timestamp and owner-approved signer, and record SHA-256 only after the final timestamped Authenticode signature is in place. Upload those same bytes to the stable release and compare the GitHub asset digest with that final SHA-256. If the executable is signed or changed again, repeat verification and re-register the asset digest.
3. Test the first in-place installation over 0.1.3, then test in-app installation from the first equipped version into a newer signed build in an isolated Windows account. Check installer interruption, subsequent launch and that the original database remains selected. An installer with missing or untrusted signing is never started by the updater. The ephemeral Windows CI test covers real Inno Setup and a disposable certificate, independent of the production signer.
